## Findings and dispositions

### Finding 1 (Blocking). PR 3 must expose an operable trusted callable admission/join boundary with App Check monitoring and meaningful per-IP/per-room throttling

As submitted, the admission transaction lived in `packages/testing/src/admissionAuthority.ts` and was callable only from emulator tests against a rules-disabled context; throttling was deferred to "PR 4 or later" on the grounds that no request context existed. The plan's PR 3 scope names the join flow including throttling, and a boundary only tests can call is not a join flow.

**Disposition — remediated, with the smallest explicit plan revision.** The trusted Cloud Functions codebase `apps/functions` (ADR-001's directory layout, already listed in `docs/TEMPLATE_ARCHITECTURE.md`) now hosts two `onCall` callables, `admitMember` and `claimSeat` (`apps/functions/src/callables.ts`, `src/index.ts`), wrapping the Admin-SDK transaction in `src/admissionAuthority.ts`. The pipeline is: App Check monitoring → `AUTH_REQUIRED` unless signed in → payload validation (`parseAdmitMemberInput`/`parseClaimSeatInput`; a malformed payload, including a client-asserted `gm`, is rejected before any Firestore read) → per-IP/per-submitted-room-code throttle → one transaction. Every denial carries the stable code in `HttpsError.details.code` with the closest gRPC status (`src/httpsErrors.ts`, exhaustive over `STABLE_ERROR_CODES`); the malformed-payload path gained its own `INVALID_REQUEST` code in the second pass (T4). The `packages/testing` duplicate and its eslint carve-out are deleted; the Admin SDK and `firebase-functions` are permitted only under `apps/functions/**`.

Throttling (`src/throttle.ts`) is a fixed 60-second window of at most 20 attempts per `(submitted room code, caller IP)`, persisted at the new service-only path `admissionThrottle/{code}/byIp/{ip}` (explicitly denied to clients in `firestore.rules`) and consumed in its own transaction before the admission transaction, so a throttled caller never reads `authority/current` or a secret hash. Keying by the *submitted* code, outside `rooms/`, bounds guesses at codes that resolve to no room (section 11's "Room-code guessing" row). The caller IP is the framework-resolved `req.ip`, falling back to the first `X-Forwarded-For` entry, then a shared `unknown` bucket — unresolvable callers are bounded together rather than exempt. `docs/PHASE_2_PLAN.md` PR 3 records this revision; PR 4 now lands in the same codebase.

What "operable" does and does not mean here: the callables are the handlers a deployed HTTPS request reaches, and the emulator suite invokes exactly those handlers (`CallableFunction.run`) against the Firestore emulator through the Admin SDK, as a deployed Function would. `npm run build` bundles the codebase to `apps/functions/dist/index.js` with esbuild (workspace packages are TypeScript sources, so a bundle is the deployable form), and `firebase.json` declares the codebase. Nothing is deployed, no region or project is named in source (`.firebaserc` carries the `staging` alias PR 3's earlier commits added alongside the unchanged `demo-digitable` default), and the Functions emulator is not started by `npm run test:emulator` (`--only auth,firestore,database`).

### Finding 2 (Blocking). General room code + passphrase must never self-claim the exclusive table capability

`decideAdmitMember` accepted a `table` request on the same `passphraseValid` boolean as a player, so anyone holding the room passphrase could take the exclusive, shared-read table seat, contradicting section 8 ("The GM admits it using a separate table code").

**Disposition — remediated.** A second service-only secret, `rooms/{roomId}/admission/tableSecret` (`RoomTableSecretDocument`), is the only secret that admits the table seat. `RoomAdmissionSnapshot` carries both `passphraseValid` and `tablePassphraseValid`; the pure decision checks the one the *requested* capability requires, so the general passphrase never satisfies a table request and the table code never admits a player or the GM. A room without a `tableSecret` document admits no table seat. The path is denied in `firestore.rules` and in the rules matrix; section 8 documents it. Covered by engine unit tests and emulator tests (general passphrase → table denied `INVALID_PASSPHRASE`, no member written; table code → player/GM denied; no table secret → denied).

### Finding 3 (Blocking). All persisted authority, room-code, binding, secret-hash, and related documents must be runtime-validated and fail closed

`readAuthorityAdmissionFields` substituted defaults for malformed fields (`roomStatus` → `active`, `admissionStatus` → `open`, `participantCount` → `0`, `tableSeatClaimed` → `false`), and bindings, code entries, and secret documents were cast without validation. A corrupted authority document would silently reopen a closed or archived room or under-report occupancy.

**Disposition — remediated.** `packages/contracts/src/room.ts` gains `parseAuthorityAdmissionFields`, `parseRoomCodeDocument`, `parseUidBindingDocument`, `parseHashedSecretDocument`, and `parseAdmissionThrottleDocument`, each throwing `RoomDataError` for any malformed or missing field. (The second pass found one gap — an absent `gmMemberId` key parsed as an open seat — fixed there, T2/C4. The recovery-hash parser exists but nothing reads `recovery/{memberId}` until PR 6.) The transaction wrapper maps `RoomDataError` to the new stable code `ROOM_DATA_INVALID` (section 6) and the transaction writes nothing. Only a genuinely absent document keeps the narrower meaning of "not found", "no binding", or "no secret to verify against" (absent secret → `INVALID_PASSPHRASE`, tested as distinct from malformed). Covered by contract unit tests over every malformed variant and emulator tests for a malformed authority document (four variants, including a missing boolean), room-code entry, uid binding (proves no second seat is minted), secret hash (two variants), and throttle counter (fails closed at the callable rather than opening a fresh window).

### Finding 4 (Blocking). Require the correct passphrase before bound-UID reclaim

Both decisions honored an `existingBinding` reclaim before checking the secret, so a stale identity could re-enter a room after its passphrase was rotated.

**Disposition — remediated, canonical docs revised.** The secret check now precedes the reclaim branch in `decideAdmitMember` and `decideClaimSeat`; reclaim still bypasses only the capacity and admission-closure checks, which apply to new occupants. Section 8 records the rule. Covered by engine unit tests (player, table, and GM wrong-secret reclaims) and emulator tests (wrong passphrase after a successful join; rotation of the stored hash locking the bound identity out until it presents the new secret; the bound table seat unable to reclaim with the general passphrase).

### Finding 5 (Blocking). Replace `ReCaptchaV3Provider` with the canonical reCAPTCHA Enterprise provider and actually initialize monitoring at the appropriate app seam

`appCheck.ts` used the classic v3 provider (section 11 specifies reCAPTCHA Enterprise) and was not called from anywhere.

**Disposition — remediated.** `initializeMonitoringAppCheck(app, env)` uses `ReCaptchaEnterpriseProvider` with `VITE_RECAPTCHA_ENTERPRISE_SITE_KEY`, returning `null` without a key. A new startup seam, `apps/web/src/firebase/bootstrap.ts`, is called once from `main.tsx` before render: it initializes the Firebase app and App Check monitoring when the Firebase configuration is present, and touches no Firebase service at all for the local-only build (which still runs the in-memory simulation). Server-side, the callables run with `enforceAppCheck: false` and log a content-free `admission.appCheckMissing` event for token-less requests. No code path can request enforcement; that remains the console-side "before public preview" gate. Covered by web unit tests (Enterprise provider chosen and v3 never constructed; exactly the monitoring options and nothing else; local-only build initializes nothing) and an emulator test (a token-less request is logged and admitted; the log contains neither the room code, passphrase, nor UID).

## Residuals for the second pass and later PRs

- **R1 (second pass).** Confirm the review reads `apps/functions/src/callables.ts`'s ordering (monitoring → auth → validate → throttle → transaction) as the intended trust boundary, and that no denial path leaks room code, passphrase, or UID into logs or error messages.
- **R2 (before enforcement, staging).** Verify against real staging traffic that `rawRequest.ip` resolves to the client rather than a client-supplied `X-Forwarded-For` entry or the load balancer; if not, switch `clientIpFrom` to the documented Google Front End `X-Forwarded-For` position. The second pass (T1/C6) showed the leftmost entry is caller-controlled where the front end appends, so the IP buckets are best-effort until verified; the per-UID bucket added there is the throttle's trustworthy bound.
- **R3 (PR 4).** Deploy packaging is proven only as a bundle build; the Functions emulator and `firebase deploy` are not exercised. Region is unset in code (defaults to `us-central1` on deploy) pending John's decision to encode the staging region in `firebase.json`/function options rather than as a decision-brief note.
- **R4 (unowned).** Room creation — minting the initial code, passphrase, table code, and empty GM seat — still has no owning PR; every admission test seeds an already-provisioned room, and the GM has no way to issue a table code yet.
- **R5 (product).** The throttle constants (60 s / 20 attempts) and the shared `unknown` IP bucket are initial values chosen for correctness under transactions, not tuned against traffic.
- **R7 (second pass).** Recorded in [`2026-09-14-phase-2-pr3-second-pass-review.md`](2026-09-14-phase-2-pr3-second-pass-review.md): two independent reviewers, no blocking findings, six Medium findings all fixed on the branch.
- **R6 (dependency hygiene).** `@google-cloud/storage` 8.1.0, pulled by `firebase-admin` 14.4.0, still depends on `gaxios` 6.7.1 → `uuid` 9.0.1 (moderate; no non-major fix). The admission callables import only `firebase-admin/app` and `firebase-admin/firestore`, so the Storage client is never loaded, but it is in the deployable tree. Options for the second pass or PR 4: an npm `overrides` pin of `uuid` to ≥ 11.1.1 under `gaxios@6` (verify `gaxios` still loads), or wait for Storage to move to `gaxios` 7. The other 5 Function-scoped advisories are the monorepo-hoisted `firebase-admin` 13 (dev tooling's copy) and would not exist in a standalone install from `apps/functions/package.json`.
