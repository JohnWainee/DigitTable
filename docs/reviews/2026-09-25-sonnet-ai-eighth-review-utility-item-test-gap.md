**Test-coverage gap found and closed (not a defect in shipped behavior).** `ComposeStep2.tsx`
nests a `<button>` ("Mark and regain Blood", the utility-item action the fifth review's tap-target
fix (`5663d7f`) sized) inside the same `<label>` that wraps the item's own pool-selection
checkbox. This is exactly the class of control this audit series exists to check (an "action
picker" checkbox with an embedded action button), but across all seven prior reviews only the
button's CSS tap-target size was ever checked — never its *click behavior*. Verified empirically
(jsdom, matching real-browser label click-forwarding semantics) that clicking the button does not
toggle the checkbox, and traced the real dispatch path end to end (`ComposeStep2` →
`PlayerDashboardScreen.handleUseUtilityItem` → the real `UseUtilityItem` command →
`decideUseUtilityItem` in `templates/eat-the-reich/src/engine.ts`) to confirm this is genuinely
correct, not accidentally so. Added one regression test,
`apps/web/test/player2/PlayerDashboard.a11y.test.tsx` ("using a utility item's nested button does
not also select it for the action pool"), reusing the file's existing `reachDashboardAsRook`
end-to-end harness: it asserts Blood starts at 0/10 and the item's checkbox starts unchecked,
clicks the button, then asserts the checkbox is still unchecked while Blood and the item's
use-count genuinely updated (proving the real command fired, not a UI-only artifact). No
production source file changed — `git diff --stat` shows exactly one file, the test.

**Independent review of the added test.** A fresh, separately-launched agent (no access to this
session's reasoning) reviewed the diff, traced the same dispatch path independently, verified the
roster fixture facts in `templates/eat-the-reich/src/roster.ts` (Iryna starts `blood: 0`; her
`rook-pocket-mirror` item has `maxUses: 3`, starts at `usesRemaining: 3`,
`useEffect: { kind: "gainBlood", amount: 2 }`), reran `npx vitest run` on the file and the full
`npm run check`, and found one genuine, non-blocking nuance: `rook-pocket-mirror` has
`poolEligible: false`, so its checkbox is natively `disabled` — a disabled checkbox cannot be
toggled by any click (direct or forwarded), so this test does not actually guard against native
label-click-forwarding markup regressions (those are moot here regardless of DOM structure); what
it does guard against is a future code-level regression that wires `onUseUtilityItem` to also call
`toggleClaimable`/`setItemIds`, which the reviewer judged the more realistic real-world regression
vector anyway. The test's comment was corrected in place to describe this accurately. Verdict:
**approve**, no false-positive risk, no incorrect fixture assumptions, no flakiness, no scope
creep — a legitimate, narrowly-targeted test-only addition.
